| DEC-009 | 2026-08-15 | For live order-status updates on both the admin Live Orders board and the customer tracking page, upgrade `setInterval`-based polling to RxJS `timer` + `switchMap` (+ `takeWhile` on the customer side), instead of building a Spring Boot SSE broadcast (`SseEmitter`) proposed by Leo | Accepted | Leo proposed a full SSE architecture (webhook → `ApplicationEvent` → `SseEmitter` registry → Angular `EventSource`). Also, on its own, SSE would not have fixed ORD-TRACK-089 — that bug is that `order.status` and `deliveryStatus` don't auto-sync (see Open Issue 11), not a push-latency problem. Given the current scale (one admin, dev/sandbox, no production deployment decided per `PROJECT-CONTEXT.md`), chose the much cheaper polling upgrade instead. Implemented in `admin-order.service.ts` (`fetchOrders()` now returns the observable instead of self-subscribing, so it composes with `switchMap`; `loadOrders()` kept unchanged for existing fire-and-forget callers), `admin-orders-board.component.ts`, and `order-status-page.component.ts`. Verified live in Chrome on both surfaces: advanced real test orders (`ORD-698781`, `ORD-485158`) via the admin API mid-poll and confirmed both the board and the customer tracker updated without a manual refresh; confirmed via the network log that the customer tracker's polling genuinely stops once a terminal status (`COMPLETED`) is reached. SSE remains a valid future option if/once production deployment and a real ADMIN-gated auth story for the stream are settled — not ruled out permanently, just not justified yet. |

| DEC-010 | 2026-08-15 | Auto-advance `order.status` (customer stepper) from `deliveryStatus` (Lalamove rider lifecycle) for delivery orders, instead of requiring an admin to always manually click "Mark Ready"/"Mark Completed" | Accepted | Closes Open Issue 11 / ORD-TRACK-089. Added `syncOrderStatusFromDelivery(Order)` in `OrderService.java`, called from inside `applyDeliveryWebhookUpdate()` — the single choke point both the real Lalamove webhook and DEC-006's manual sync already funnel through, so this is naturally idempotent and self-heals any order that got stuck before this existed, the next time its delivery status is synced (no backfill needed). Two rules, delivery orders only, never touching an order already `COMPLETED`/`CANCELLED`: (1) `deliveryStatus == COMPLETED` → `order.status = COMPLETED`; (2) `order.status == PREPARING` and (`driverName` set, or `deliveryStatus` is `ON_GOING`/`PICKED_UP`) → `order.status = READY` — deliberately the exact same condition `admin-orders-board.component.ts`'s `canMarkReady()` already uses to unlock the manual button, so this doesn't introduce a new judgment call, just automates an existing one. Manual "Mark Ready"/"Mark Completed" buttons are left working as a fallback/override. Pickup orders are entirely unaffected (`applyDeliveryWebhookUpdate` only ever matches orders with a `lalamoveOrderId`, which pickup orders never have). Deliberately did *not* pursue the alternative (making the stepper itself delivery-aware with distinct steps) — bigger scope, separate future ticket if wanted. Verified live: restarted the backend, used `backend/scripts/simulate-lalamove-webhook.js` to send a real signed `DRIVER_ASSIGNED` webhook against a real `PREPARING` order (`ORD-485158`) — confirmed `order.status` flipped to `READY` immediately; then simulated the full `ON_GOING → PICKED_UP → COMPLETED` sequence — confirmed `order.status` flipped to `COMPLETED` in step with `deliveryStatus`. Order reverted (via direct H2 update, since there's no API to reset `deliveryStatus`/driver fields) to its exact pre-test state afterward. |

| DEC-011 | 2026-08-15 | Make the customer order-tracking stepper delivery-aware — a distinct 5-step sequence for delivery orders (`Order Received → Preparing → Rider Assigned → Picked Up → Delivered`) instead of relabeling the 4-step pickup sequence, plus a separate failure banner for a rejected/canceled Lalamove delivery | Accepted | Follow-up to DEC-010, which left this explicitly deferred as bigger scope. Chose the fuller option over a cheaper label-only swap (offered, not taken) so a delivery customer sees Lalamove's real rider lifecycle instead of generic pickup wording. Needed no backend/API changes — `deliveryStatus`/`driverName` were already exposed on the public `publicView()` response and already typed on the shared `Order` model, just unused by the stepper. Implementation: `order-status-stepper.component.ts` now takes `fulfillmentType`/`deliveryStatus` inputs and picks between `PICKUP_STEPS` (unchanged) and a new `DELIVERY_STEPS` array; `currentIndex` treats `order.status` as authoritative for the coarse stage and only uses `deliveryStatus` to split the single `READY` stage into "Rider Assigned" (index 2) vs "Picked Up" (index 3) — deliberately not "Out for Delivery" for index 2, since DEC-010 advances to `READY` as soon as *either* a driver is assigned *or* Lalamove reports `ON_GOING`/`PICKED_UP`, so the rider may not have physically picked up yet at that point. Also added a `isDeliveryFailed()` banner ("Your delivery couldn't be completed. Please contact the store.") for the case DEC-010 doesn't cover — Lalamove `REJECTED`/`CANCELED` while `order.status` is still non-cancelled, which the stepper couldn't otherwise represent as a forward step. `order-confirmation.component.ts` got the same stepper inputs for consistency (no polling there, so no failure-banner branch needed in practice). Caught and fixed one real bug during this work: the initial `@for (step of steps; track $index; let i = $index)` syntax failed Angular's template compiler (`NG9: Property '$index' does not exist`) — fixed by referencing `$index` directly in the template body instead of aliasing it via `let i = $index` alongside the `track` clause. Separately discovered mid-verification that the frontend dev server (running since the prior day) had stopped picking up file changes entirely — restarted it, which is what actually surfaced the compiler error above. Verified live in Chrome against real orders: walked a real delivery order through all 5 states via `simulate-lalamove-webhook.js` (`DRIVER_ASSIGNED` → `ON_GOING`/`PICKED_UP` → `COMPLETED`) confirming each step's icon, ring highlight, and message text; simulated a `REJECTED` event on a second order confirming the failure banner replaces the stepper; placed and walked a fresh synthetic pickup order through `RECEIVED → PREPARING → READY` confirming the original 4-step pickup path is unaffected. All test orders reverted/cancelled afterward. |
