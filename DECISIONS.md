| DEC-007 | 2026-08-15 | Finish wiring `publicToken` (added in `f1eb8c7`) as the *only* key the public order-tracking endpoint accepts, instead of `orderNumber` | Accepted | `OrderController.getOrder` / `OrderService.getOrderStatus` now resolve by `publicToken` via `findByPublicToken`, returning `publicView()`. | DEC-008 | 2026-08-15 | Wire `existsByGcashReference` (added in `f1eb8c7`, previously unused) into `placeOrder` to reject a GCash order whose OCR-extracted reference was already used by a prior order | Accepted | In `OrderService.placeOrder`, after `applyReceiptImage` runs OCR, if the extracted `gcashReference` is non-blank and `existsByGcashReference` returns true, the order is rejected with `409 CONFLICT` before it's ever saved (the receipt file is still written to disk at that point — an existing, unchanged behavior shared with every other post-upload validation failure in this method, e.g. a bad product id). The check is on the *whole* orders table regardless of status, so a reference tied to an already-cancelled order still blocks reuse — intentional, since the fraud case is "reuse the same payment proof," not "reuse it against a still-open order." Verified live against the real backend/OCR/H2: reused an already-used receipt image (same OCR'd reference as an existing order) → `409` with the expected message; a synthetic receipt image with a freshly-generated, never-seen 13-digit reference → `201`, order placed normally. Both test orders created during verification were cancelled afterward. |
| DEC-009 | 2026-08-15 | For live order-status updates on both the admin Live Orders board and the customer tracking page, upgrade `setInterval`-based polling to RxJS `timer` + `switchMap` (+ `takeWhile` on the customer side), instead of building a Spring Boot SSE broadcast (`SseEmitter`) proposed by Leo | Accepted | Leo proposed a full SSE architecture (webhook → `ApplicationEvent` → `SseEmitter` registry → Angular `EventSource`). Reviewed it and flagged real risks: the proposed endpoint would broadcast full unredacted order objects (guest name/phone/email/address) and the plan's own suggested fix for Spring Security blocking it — `permitAll` or JWT-in-URL — would make that an unauthenticated PII leak (this is exactly what DEC-007 redacted `publicView()` for); an in-memory `CopyOnWriteArrayList<SseEmitter>` only works single-instance, which is fine today but silently breaks if ever scaled horizontally; and the whole mechanism is downstream of the Lalamove webhook, which we already know is unreliable locally (see `docs/lalamove-webhook-tunnel.md`) so DEC-006's manual sync can't be retired regardless. Also, on its own, SSE would not have fixed ORD-TRACK-089 — that bug is that `order.status` and `deliveryStatus` don't auto-sync (see Open Issue 11), not a push-latency problem. Given the current scale (one admin, dev/sandbox, no production deployment decided per `PROJECT-CONTEXT.md`), chose the much cheaper polling upgrade instead. Implemented in `admin-order.service.ts` (`fetchOrders()` now returns the observable instead of self-subscribing, so it composes with `switchMap`; `loadOrders()` kept unchanged for existing fire-and-forget callers), `admin-orders-board.component.ts`, and `order-status-page.component.ts`. Verified live in Chrome on both surfaces: advanced real test orders (`ORD-698781`, `ORD-485158`) via the admin API mid-poll and confirmed both the board and the customer tracker updated without a manual refresh; confirmed via the network log that the customer tracker's polling genuinely stops once a terminal status (`COMPLETED`) is reached. Test orders were reverted to their prior state afterward. SSE remains a valid future option if/once production deployment and a real ADMIN-gated auth story for the stream are settled — not ruled out permanently, just not justified yet. |
